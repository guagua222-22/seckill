# 秋招讲解与简历描述

学习目标：能画出一次请求，指出每一层的事务边界，再用测试和指标解释为什么这样设计。面对“这个步骤成功、下一步失败怎么办”，能推演出状态才算掌握。

## 1. 简历项目描述定稿

**项目：高并发秒杀系统（个人学习项目）**

**技术：** Java 21、Spring Boot、Spring Cloud Alibaba、MySQL、Redis、RocketMQ、Sentinel、Micrometer、Prometheus、Grafana。

- 将单体演进为用户、商品库存、秒杀订单与网关四个服务，按业务域拆分三库；通过 Feign、Nacos 与 LoadBalancer 完成调用和实例发现，使用名称快照减少跨服务查询。
- 设计 Redis Lua 原子预扣、本地消息表与 RocketMQ 异步落单链路，结合数据库条件更新、唯一约束、消费去重和库存操作流水处理并发竞争与重试，并梳理跨库补偿的故障窗口。
- 接入 Sentinel 入口与热点参数限流、依赖异常比例熔断，使用 Caffeine 热点缓存和 Redisson 分布式布隆降低重复访问；按 HTTP 状态与业务码分别验证限流结果。
- 建立 Micrometer → Prometheus → Grafana 监控链路，交付 16 个面板、5 条基础告警和库存有界采集；保留 100 个默认 Java 测试及 Windows 一键启动、状态检查和安全停止脚本。

以上适合当前实现。不要写“真实承载百万用户”“零丢单”“分布式事务完全闭环”。若简历空间有限，保留前三条，把监控合并为一句。需要量化性能时，先按 [性能模板](performance-run-template.md) 重跑并保存原始记录，再加入接口、并发、实例数、业务成功率及 P95；历史数字的边界见 [性能文档](performance.md)。

## 2. 30 秒版本

> 我做了一个从单体逐步演进的秒杀学习项目。先用数据库条件扣库存和唯一索引控制并发，再通过 Redis Lua 做准入、RocketMQ 异步落单，把洪峰缓冲起来。拆成微服务后，我重点处理请求幂等和跨库补偿，并接入限流、热点缓存与监控。现在既能说明正常请求怎么走，也在通过故障窗口审查推进一致性验证。

## 3. 两分钟版本

> 最开始是 DB 直接扣库存并插订单，同库事务比较清晰，但所有请求同步竞争数据库。后来我在入口加 Redis Lua，把库存判断、资格判重和预扣做成一个原子步骤。
>
> 预扣成功后，在秒杀库同一个事务里写请求流水和待发消息，再发送 RocketMQ。接口先返回排队结果，消费者负责调用商品服务扣 DB 库存、插订单，再推进流水。发送失败可以从消息表重发，重复投递通过去重标记、锁和数据库约束处理。
>
> 微服务拆分之后，我特别区分本地事务与远端提交：商品库存和订单分属两个库，一个注解不能把两边一起回滚。库存操作按 requestId 留流水，但补偿失败和 Lua 到消息表之间的宕机窗口仍需要独立恢复协议，不能仅凭“用了 MQ”就说不会丢单。
>
> 对性能和稳定性，我加了热点配置的 Caffeine 缓存、Sentinel 限流和依赖熔断，再用 Micrometer、Prometheus、Grafana 看吞吐、尾延迟、拒绝数和库存趋势。压测同时统计 HTTP 状态和业务码，防止把快速拒绝误当作成功吞吐。项目默认有 100 个 Java 测试；真实故障注入和生产部署能力还有明确待办。

## 4. 常见追问怎么回答

### 为什么 Lua 了还要 DB 条件扣库存？

Lua 管 Redis 的并发资格与预扣，DB 管最终库存事实。两者失败恢复的边界不同，Redis 预扣成功不等于订单已提交。数据库 `available_stock > 0` 的条件更新防止库存减为负，唯一索引限制重复订单；但唯一订单仍不能单独证明库存只扣了一次，需要查库存操作流水。

### 本地消息表解决了什么，没解决什么？

解决了本地流水已提交之后，发送意图可以被重新扫描。broker 确认丢失还可能造成重复发送，因此消费者仍需幂等。它没有原子地覆盖之前的 Redis Lua，也没有覆盖之后的远端库存事务。画出 [时序图](architecture.md) 的三段提交边界最容易说清。

### 为什么三层幂等，直接加锁不行吗？

SETNX 减少重复进入，锁减少并发碰撞，唯一约束限定数据库最终可提交的数据。标记和锁会过期，处理还可能中断，因此持久状态必须参与重入判断。当前消费者设置固定锁租期，不能泛泛说“Redisson 看门狗保证一直持锁”。

### 微服务的 @Transactional 能回滚 Feign 吗？

不能。它只管理当前事务管理器覆盖的数据库连接。goods 事务提交后，seckill 本地异常不会自动撤销远端提交。需要幂等补偿和可恢复状态，或者另选全局事务方案并承担它的成本。当前实现没有 XA；代码里吞掉异常还会影响本地回滚，应通过真实数据库测试确认。

### 怎么防缓存穿透、击穿、雪崩？

分别解释布隆和空值缓存过滤无效查询、逻辑过期与互斥重建减少已有热点过期时的回源、随机 TTL 分散过期时点。当前重建者同步回源，不是线程池异步刷新；物理 key 不存在的冷启动分支还需单独保护。布隆装载不完整可能在业务上误拒绝存在的数据。

### Caffeine 库存旧了会不会超卖？

本地缓存主要放基础信息和活动配置，交易库存每次由 Lua 判断；详情里的 DB 库存也单独查询。配置短暂旧值与交易库存原子扣减是不同问题。仍需考虑活动时间、价格变更和本地 TTL 的一致性要求，而不是简单回答“缓存可以随便旧”。

### 熔断和限流的区别？多实例阈值会怎样？

限流控制进入的速率，熔断在依赖错误较多时暂时减少调用。本项目按异常比例熔断，普通业务拒绝不视为系统故障。默认 Sentinel 规则是实例内的，新增实例会增加合计配额；固定总配额需要统一入口或专门的集群限流设计。

### Redis 挂了怎么办？

设计意图是 DB 直写降级，但当前活动缓存读取在捕获范围外，冷缓存时可能提前失败；不能承诺全故障自动无损切换。还要验证降级对 DB 的压力和恢复时 Redis/DB 一致性。这是 [已知边界](known-limitations.md) 中优先修复和验证的项目。

### 为什么不直接看前端轮询统计？

前端打开与否会影响观测，难以聚合多实例和保留历史。Prometheus 按固定周期抓取服务指标，Grafana 查询时间序列；业务拒绝用单独计数器补足 HTTP 200 的信息。库存采集在后台限量执行，抓取端只读内存，避免每次抓取都查 Redis。

### P95 是什么？为什么不能平均各实例 P95？

P95 表示约 95% 的观测不超过该值；每个实例的分位数不能直接平均得到全局分位数。当前 HTTP 直方图先按桶累加速率，再计算集群分位数。入口 RT 不包含 MQ 排队和消费，最终落单延迟还需另外测量。

### 项目最有价值的一次排查是什么？

可以选“限流统计中的 HTTP 200/业务 429”或“事务捕获异常导致的库存幂等边界”。按现象 → 假设 → 源码/数据证据 → 验证方法 → 结论组织，不把未复现风险编造成已经处理过的线上事故，也不要把别人完成的工作说成独立经历。

## 5. 推荐的学习顺序

1. 对着架构图，自己讲一次请求从入口到查单，把每次 Redis、Feign、DB、MQ 访问标出来。
2. 读 `SeckillOrderServiceImpl`、`RecordMessageWriter`、`DbOrderWriter`、`StockOperationServiceImpl`，回答每个步骤提交后宕机会留下什么。
3. 跑小流量详情请求，看 HTTP QPS、P95、Caffeine 命中率；再解释“无数据”和“数值 0”的区别。
4. 选一个 P1 缺口，先设计能失败的真实集成测试，再改代码、验证恢复和重试。一次只解决一个事务边界。
5. 脱离文档口述两分钟，再接受三个追问：消息重复怎么办、补偿又失败怎么办、你的性能数字统计了什么。

讲到不能确定的地方，指出证据缺口和下一步实验即可。准确承认边界，比承诺一套未经验证的“生产级保证”更有说服力。
