# 性能数据与复测方法

首先分清四个数字：请求吞吐、入口受理吞吐、最终落单吞吐、限流拒绝吞吐。它们可能相差很大。请求快速返回“重复购买”，只能证明拒绝路径很快，不能证明同样速度创建了订单。

## 2. 指标口径

| 指标 | 推荐定义 |
|---|---|
| 客户端请求吞吐 req/s | 本轮发出的请求数 / 实际耗时，同时单列传输错误 |
| 入口受理率 | 秒杀接口 code=0 数 / 秒杀请求数；正常异步路径只是进入排队 |
| 最终订单成功率 | 等待消费和重试收敛后，按本轮请求集合查到的有效订单数 / 本轮请求数 |
| 最终落单 TPS | 固定观察窗口内新提交订单数 / 窗口时长；说明是否包含积压消化阶段 |
| HTTP RT | 从客户端发起到读取完响应，不含异步消费等待 |
| 端到端落单延迟 | 同一 requestId 从入口接收到订单提交；需要相关时间戳，当前监控未完整提供 |
| 库存正确性 | 按本轮专用商品对比初末库存、有效订单、库存操作状态；Redis/DB 先等收敛再比较 |

不要把 HTTP 200 计为业务成功。网关拒绝可以是 HTTP 429，服务内部拒绝可以是 HTTP 200 + code=429。现有 [Node 脚本](../scripts/loadtest/load.mjs) 已按两者分类，但 RT 混合所有响应，不能从它的总体 P99 推导成功路径 P99。脚本不保存逐请求 requestId/延迟明细，严格的端到端测量需补充采集能力。

## 3. 从小流量复现读取场景

先按 [运行手册](runbook.md) 启动，选验证台已有且可读的商品。Node.js 18+ 即可，不需 npm 依赖。以下只演示详情 GET，不创建交易：

```powershell
$goodsId = '替换为已有商品ID'
$runName = Get-Date -Format 'yyyyMMdd-HHmmss'
New-Item -ItemType Directory -Force logs/benchmarks | Out-Null
# 先确认 100 次小流量均成功；日志包含业务错误分类
node scripts/loadtest/load.mjs --mode detail --base http://localhost:8080 --goods $goodsId --total 100 --concurrency 5 |
    Tee-Object "logs/benchmarks/$runName-detail-smoke.txt"
```

小流量验证通过后，再自行逐档提高并发 10 → 50 → 100，观察错误码、成功路径延迟、CPU/GC 和数据库压力。每档留出预热和稳定观察时间，重复至少三次；不要一开始就把失败请求和限流吞吐当成性能收益。

对比 Caffeine 热点开关时，使用同一商品、相同入口、同样实例数、数据量、JVM 参数与限流配置，仅改变热点配置。记录缓存失效/预热过程，交替执行 A/B，报告每次结果而不是只挑最好的一次。服务和压测机共用机器时，客户端也可能成为瓶颈。

## 4. 交易实验需要额外准备

交易压测会写用户、活动、订单和库存，只在专用测试数据集执行。活动必须处于当前时间窗内，先预热；验证成功吞吐要有足够多不同用户，反复轮转五个用户大多会命中一人一单拒绝。

建议分为三组，分别解释结果：

1. **库存竞争：** 足量不同用户抢较少库存。收敛后有效订单不超过初始库存，用户/活动不重复，DB 库存不为负；检查 Redis 资格与 DB 结果的一致性。
2. **重复投递：** 同 requestId、同用户不同 requestId 分别测试；区分订单幂等与库存扣减幂等，不能仅查订单数。
3. **故障恢复：** 消息发送失败、goods 提交后响应丢失、订单插入失败等，在独立环境注入故障并核对补偿流水，标准见 [已知边界](known-limitations.md)。

现有历史 e2e 有失效日期和跳过条件问题，修复之前不把它作为这些场景的自动验收。M8 不为补齐曲线对你的现有活动执行写入压测。

## 5. 每次实验必须留下记录

复制 [结果模板](performance-run-template.md)，填入代码提交、环境、命令、初始数据和全部结果。原始输出可先保存在被忽略的 `logs/benchmarks/`；正式用于简历的证据应脱敏后随对应报告提交，避免只剩一个数字。

解释瓶颈要有证据：RT 上升可能来自排队、Feign、Redis、数据库锁、GC 或客户端饱和。Prometheus 曲线能缩小范围，确诊往往还需慢查询、线程栈、剖析或链路追踪。当前没有这些证据时，就说“观察到吞吐差异，原因待定位”。
